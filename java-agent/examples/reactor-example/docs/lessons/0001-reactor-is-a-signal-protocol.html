Reactor 是信号协议，
不是异步魔法

第一步：从“我写了什么”转向“订阅时发生了什么”。

你熟悉 Spring Boot 的业务代码。学习 Reactor 的关键，不是先背一堆操作符，而是能回答：谁启动了这条处理链？数据如何流动？它何时才会执行？

一条链有两个方向

Publisher ── onNext / onError / onComplete ──▶ Subscriber
Publisher ◀──────── request(n) / cancel() ───── Subscriber

Reactive Streams 把生产者、消费者和订阅控制分开：Publisher 发布序列，Subscriber 接受信号，Subscription 是订阅建立后两边控制需求/取消的把手。数据往下游走，需求往上游走。这是背压（backpressure）机制的协议基础。

在 Reactor 中，Mono<T> 表示 0 或 1 个元素，Flux<T> 表示 0 到多个元素；它们提供描述与组合处理过程的 API。但仅仅创建和组合 publisher，通常只是构造处理描述，不等于结果已经被消费。

API 体验：组装不等于订阅

Flux flow = Flux.range(1, 3)
    .doOnNext(n -> System.out.println("处理 " + n));

System.out.println("组装完成");
flow.subscribe();

先自己预测输出顺序，再点按钮核对。关键观察：没有订阅之前，doOnNext 里的处理还没有被触发。调用 subscribe() 后订阅开始，才看到元素经过操作链。

快速预测

把控制台输出看成一条时间线：哪行必定先出现？

先打印“组装完成”，再依次打印“处理 1”“处理 2”“处理 3”。创建 flow 时只是构造链；显式订阅后，这个同步 range 源立即供数。注意：这是这个例子的执行方式，不代表 Reactor 的所有链都运行在异步线程上。

重要限定：不要把“订阅前什么都不会发生”当成所有 Publisher 的定律。cold publisher 通常每位订阅者各自触发一次执行；hot publisher 可以独立于订阅者产生事件。just(value) 还会在组装时就捕获 value。请区分“构造处理链”“订阅”“源的热/冷语义”。

为什么生产代码不应随手 subscribe？

在 WebFlux 等框架边界，框架通常负责订阅并把响应交给调用方。若在链中间手动 subscribe()，容易把工作切成脱离主流程的 fire-and-forget：错误、取消、完成时机可能不再由上游调用者管理。通常应返回并组合 Mono/Flux，只在真正的命令式边界订阅，并显式处理生命周期。

本课带走

  • Reactor 类型描述流；Reactive Streams 协议控制订阅与需求。
  • 数据向下游，需求/取消向上游。
  • 组装与执行是不同阶段；订阅通常启动 cold publisher 的处理。
