订阅之后，
数据为什么还没来？

本课目标：预测一次订阅中的信号顺序，并用 request(n) 控制接收数量。

为了读懂 Reactor 的底层调用过程，这一课先追踪一个最小同步源。你已经能区分“重新执行源”和“重放历史”；现在观察另一件事：订阅关系建立后，下游如何告诉上游自己需要多少数据。

先凭记忆回答

一个温度源保存了上次测量结果，新订阅者直接拿到它，没有重新测量。这是重新执行，还是重放？先说出理由，再展开。

核对

这是重放：订阅没有触发新的测量。能收到历史数据，不能单独作为判断 cold 的依据。

先建立关系，再表达需求

Subscriber ── subscribe ──▶ Publisher
Subscriber ◀─ onSubscribe(subscription) ── Publisher
Subscriber ── request(2) ──▶ Publisher
Subscriber ◀─ onNext(1) ──── Publisher
Subscriber ◀─ onNext(2) ──── Publisher
                  暂停：剩余需求为 0
Subscriber ── request(1) ──▶ Publisher
Subscriber ◀─ onNext(3) ──── Publisher
Subscriber ◀─ onComplete ── Publisher

onSubscribe 把 Subscription 交给订阅者。订阅者通过它调用 request(n)：增加 n 个元素的接收额度。每收到一个 onNext，额度消耗一个；多次请求可以累加。源可以少发，也可以稍后再发，但不能超出已请求的数量。[规范 §1.1、§1.9]

本课限定：使用没有额外预取操作符的 Flux.range(1, 3)，它按需求同步供数。Hot 源中的外部事件仍可能发生，但向每个订阅者发送的 onNext 也必须遵守需求；缓存或丢弃等行为由具体实现决定。

在 Java 中观察同一过程


普通的 subscribe(value -> ...) 默认请求 Long.MAX_VALUE，表示不限制需求，因此第一课里看不到“等待请求”的阶段。这里用 BaseSubscriber 覆盖默认行为。[官方：请求与背压]


BaseSubscriber<Integer> learner = new BaseSubscriber<>() {
    @Override
    protected void hookOnSubscribe(Subscription s) {
        System.out.println("onSubscribe：已建立订阅，暂不请求");
        // 故意不调用 request，改由下面的代码请求。
    }

    @Override
    protected void hookOnNext(Integer value) {
        System.out.println("onNext " + value);
    }

    @Override
    protected void hookOnComplete() {
        System.out.println("onComplete");
    }
};

Flux.range(1, 3)
    .doOnRequest(n -> System.out.println("request " + n))
    .subscribe(learner);

learner.request(2); // 同步收到 1、2，然后返回。
learner.request(1); // 同步收到 3、完成，然后返回。


BaseSubscriber 保存了订阅句柄，所以这里可以从外部调用它的 request。省略请求是为了观察暂停；实际使用时需要确保最终提供需求。[官方：BaseSubscriber]


完整代码含导入和错误回调：RequestDrivesSignals.java。在 IDE 中运行它的 main，重点观察“subscribe 已返回”和两次 request 之间的日志。

一个容易漏掉的区别


需求额度只约束 onNext。onComplete 和 onError 不消耗额度：空源可以直接完成，发生错误也不需要先等到请求。完成与错误是两种终止方式；终止后，不再发送后续信号。[规范 §1.2、§1.7]

带走一个判断方法


看到“订阅了但没数据”，先问：订阅关系建立了吗？下游发出需求了吗？源是否已经有数据可发？request(n) 表达接收额度，本身不负责切换线程，也不保证立即得到 n 个元素。
